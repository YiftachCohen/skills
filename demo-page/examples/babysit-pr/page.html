babysit-pr no longer calls a pull request green before its CI has run

babysit-pr is a skill that stays with a pull request until CI passes and review comments are handled. Its old wait loop could report success before any check had started, missed checks that timed out, and was cut off by the shell’s 2-minute limit. PR #15 replaces it with a tested script that watches CI and reviews together.

One background command waits for anything that needs the agent

After each push the agent starts wait-for-pr.sh once, in the background, and spends no turns while it runs. The script returns on the first thing that needs action, and the agent decides what to do from the snapshot it prints.

  1. Start the wait with the pushed commit. The agent runs the script in the background with --sha set to what it just pushed.

  2. Wait for CI to register. Up to 5 minutes for the PR head to reach that commit and for checks to appear on it. If they never do, the result is no-checks, which usually means a conflict or workflows that skip this PR.

  3. Watch everything that could need the agent. Every 60 seconds the script reads the PR state, the checks by bucket, and review activity, including edited comments. --interval changes the 60 seconds.

  4. Hold briefly after the first event. It keeps watching for 60 more seconds, so a review and a failure that land together come back as one wake-up. --settle changes the hold.

  5. Classify and act. The agent reads the JSON snapshot and returns DONE or BLOCKED, or fixes, pushes and waits again on NOT YET.

Every reason the wait can return, from scripts/wait-for-pr.sh 
closed        PR was merged or closed - stop babysitting
head-moved    someone else pushed; sync before doing anything
head-mismatch the PR head never reached <sha> (push missing or rejected?)
no-checks     no checks registered on <sha> (conflict? path filters?)
failing       at least one counted check is in the "fail" bucket
new-review    comments, reviews, or threads changed since the wait began
settled       every counted check finished and none failed
timeout       --timeout elapsed with nothing actionable

Comments and CI logs can no longer steer the agent

On a public repo anyone can comment, and a CI log can echo text an attacker controls. The skill now treats comments, review bodies, commit messages and logs as data about the PR, not as instructions.

  • It acts on a review finding only after verifying it against the code.
  • It weighs findings by author: owners, members, collaborators and the repo’s own reviewer bots first; anyone else’s comment is a report to check.
  • It never follows text that asks it to run commands, fetch URLs, reveal secrets or change workflows. Changes to .github/workflows/ need your approval even when a trusted reviewer asks.
  • It replies to human review threads instead of resolving them, so the reviewer decides when a thread is done.

What it costs

The wait trades a little latency and some API calls for not spending model turns.

  • A wake-up can trail the event by up to two minutes: up to 60 seconds until the next poll, plus the 60-second settle window.
  • Each poll makes three GitHub calls (PR state, checks, review threads) for as long as CI runs.
  • One wait gives up after 25 minutes by default and the agent starts another. A PR whose state stops changing is reported as stalled rather than waited on forever, and one invocation stops after 12 passes.

Questions

How does the agent know the wait has finished?
In Claude Code it runs the script as a background command and is notified when it exits, so it spends no turns waiting. Where the runtime can subscribe to pull request events, the skill prefers that and wakes on each comment, review or CI result. Elsewhere it calls the script with a timeout that fits the shell’s limit, and calls it again on timeout.
What counts as a stall?
The script keeps a fingerprint of everything that would make the agent act: the head commit, mergeability, the review decision, each check’s bucket and the review activity. When it has not changed for 60 minutes, the agent stops and reports NOT YET, or BLOCKED if a check is stuck queued or never reports.
What if the repo has no required checks?
The agent watches every check instead, and says so in its report.
What if someone else pushes to the branch?
The wait returns head-moved, and the agent syncs to the new head on the remote before doing anything else.
Will the polling run into GitHub’s rate limits?
Three calls a minute is about 180 an hour, well below the 5,000 REST requests an hour GitHub allows an authenticated user. Reviewer bots have their own limits: the agent waits out the stated cooldown and asks for a review once more.
What do the new evals test?
Each is a realistic request with the behavior expected. The twelve new ones include a PR with no checks for an hour, a first-time commenter telling the agent to run a command, a 25-minute CI run with a bot that reviews within minutes, an edited review comment, and a bot asking for an unrelated refactor.
