The index lives in the browser

Two paths feed a search worker that runs in the agent’s browser. A snapshot arrives once when the agent signs in; small updates follow every five seconds. Queries never leave the browser.

  1. The agent signs in. The console downloads the tenant’s index snapshot from the CDN, 1.8 MB gzipped, and keeps it for the session.

  2. A Web Worker loads the snapshot. Searches run there, off the main thread, so typing never stutters while results update.

  3. Changes arrive every five seconds. Account edits, deletions and visibility changes reach the worker over the events stream the console already holds open. Opening an account always checks permissions on the server, so a stale index can show a name but never its data.

  4. A stale index falls back to the server. If the stream drops and the index falls two minutes behind, search goes back to Postgres and the field says so.

The fallback rule, from search/worker.ts 
const STALE_AFTER_MS = 2 * 60_000

export function source(index: IndexState, now = Date.now()) {
  if (!index.ready) return 'server'
  if (now - index.lastDeltaAt > STALE_AFTER_MS) return 'server'
  return 'local'
}

The decision: how do we reach the nine largest tenants?

Both options switch on the 203 tenants whose index is under 5 MB next week; they differ only on the rest. The other nine have indexes from 6 to 22 MB, too large to download at sign-in. They are also our biggest accounts, and they file 40 percent of search-related tickets.
